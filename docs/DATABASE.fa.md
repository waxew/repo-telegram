# دیتابیس و ذخیره‌سازی

## آیا می‌توان همه‌چیز را داخل خود تلگرام ذخیره کرد؟

خیر. Telegram Bot API برای ذخیره‌ی ساختاریافته‌ی محصولات، سفارش‌ها، کاربران، موجودی و تنظیمات طراحی نشده است. تاریخچه‌ی چت نیز دیتابیس قابل Query و تراکنش مالی نیست. اگر ربات Restart شود یا پیام‌ها پاک شوند، اتکا به state داخل حافظه یا چت باعث از دست رفتن فرایند می‌شود.

تلگرام برای این پروژه دو چیز ارزشمند نگه می‌دارد:

- پیام‌های ورودی و خروجی
- `file_id` رسانه‌ها که همان ربات می‌تواند بعداً بدون آپلود دوباره ارسال کند

بقیه‌ی اطلاعات در PostgreSQL ذخیره می‌شود.

## جدول‌های پروژه

- `telegram_shop_builder_accounts`: حساب سازنده‌ها
- `telegram_shop_bots`: ربات‌های مشتری، توکن رمز‌شده و تنظیمات
- `telegram_shop_users`: کاربران و کیف پول مستقل هر فروشگاه
- `telegram_shop_sessions`: مرحله‌ی ویزاردهای چندپیامی
- `telegram_shop_categories`: دسته‌بندی‌ها
- `telegram_shop_products`: اطلاعات محصول و محتوای تحویل
- `telegram_shop_plans`: پلن‌ها و قیمت‌ها
- `telegram_shop_discount_codes`: تخفیف ثابت و سقف استفاده
- `telegram_shop_orders`: سفارش، snapshot تحویل و کد پیگیری
- `telegram_shop_transactions`: دفترکل غیرقابل‌حذف کیف پول
- `telegram_shop_topups`: شارژ کارت/زرین‌پال و وضعیت بررسی
- `telegram_shop_support_messages`: تیکت‌های پشتیبانی
- `telegram_shop_broadcasts`: صف پیام همگانی

## جداسازی فروشگاه‌ها

تقریباً همه‌ی جدول‌ها `shop_id` دارند. تمام Queryهای Repository این شناسه را اعمال می‌کنند. پلن‌ها از طریق محصول به فروشگاه متصل‌اند و قبل از ویرایش، رابطه‌ی آن‌ها دوباره بررسی می‌شود.

## عملیات مالی

تابع `telegram_shop_checkout` ردیف کیف پول را با `FOR UPDATE` قفل می‌کند، پلن و کد تخفیف را داخل همان تراکنش اعتبارسنجی می‌کند، موجودی را کم می‌کند، سفارش و دفترکل را می‌سازد و پاداش معرف را فقط یک‌بار می‌دهد.

تابع `telegram_shop_approve_topup` نیز رسید را قفل می‌کند و فقط اگر هنوز `pending_review` باشد، کیف پول را شارژ می‌کند. بنابراین دوبار زدن دکمه تأیید یا تکرار کال‌بک زرین‌پال موجودی را دوبار زیاد نمی‌کند.

## امنیت Supabase

- RLS روی تمام ۱۳ جدول فعال است.
- `anon` و `authenticated` هیچ مجوز جدولی ندارند.
- توابع مالی `SECURITY INVOKER` هستند و RLS را دور نمی‌زنند.
- فقط Worker با `SUPABASE_SECRET_KEY` کار می‌کند.
- کلید محرمانه هرگز به ربات مشتری، پیام تلگرام یا کد سمت مرورگر ارسال نمی‌شود.

هشدار INFO مربوط به «RLS بدون policy» عمدی است: policy نداشتن در کنار RLS یعنی default deny. چون این پروژه هیچ دسترسی مستقیم مرورگر به دیتابیس ندارد، این حالت مطلوب است.

## بکاپ

مالک از پنل مدیریت فایل SQL همان فروشگاه را می‌گیرد. جدول‌ها با فیلتر tenant خوانده می‌شوند، داده‌ی فروشگاه دیگر وارد خروجی نمی‌شود و `ON CONFLICT DO NOTHING` بازیابی دوباره را کم‌خطرتر می‌کند.
